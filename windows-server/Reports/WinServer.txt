## 3. Active Directory Domain Services (AD DS)

### 3.1 Domain Promotion

After installing the AD DS role, the server was promoted to a **Domain Controller** for the new forest `uni.local`. During promotion:
- **Forest and Domain Functional Level** were both set to Windows Server 2016.
- The **DNS Server** option was enabled during promotion so the DC also acts as the primary DNS server.
- A **DSRM (Directory Services Restore Mode)** password was configured for recovery scenarios.
- The **NetBIOS domain name** was confirmed as UNI.

### 3.2 Organizational Unit (OU) Structure

Three top-level **Organizational Units** were created directly under the `Uni.local` domain root to mirror the university's department structure:

| OU Name | Target Population |
|---|---|
| `uni_Student` | Student users and their workstations |
| `uni_Staff` | Faculty/staff users and their workstations |
| `uni_Management` | Administrative/management users and workstations |
| `uni_Groups` | Security groups for RBAC |
| `NetworkAdmin` | Network administration accounts |

This OU design is the foundation of the entire security model — every Group Policy, every permission assignment, and every access control decision flows from which OU a user or computer object lives in.

### 3.3 User Accounts

User accounts were created inside their respective OUs. Each account was configured with:
- A **username** following a naming convention (e.g., Student 1, Student 2, Student 3).
- An **initial password** set by the administrator.
- A **Description** field populated with the VLAN/department tag (e.g., "Vlan 10 | Students", "Vlan 40 | Students") for easy identification and auditing.
- **Domain authentication**, allowing login from any domain-joined workstation.

Confirmed user accounts visible in `uni_Student`:
- Student 1 — Vlan 10 | Students
- Student 2 — Vlan 10 | Students
- Student 3 — Vlan 40 | Students

### 3.4 Computer Accounts (Domain-Joined Workstations)

The following Windows 10 client machines were joined to the `uni.local` domain and their computer objects were moved into the correct OUs:

| Computer Name | Description | OU |
|---|---|---|
| DESKTOP-M65LJ28 | Management workstation | uni_Student / Management |
| STUDENT | win_10.1 (Student) | uni_Student |
| STUDENT-TWO-V10 | win_10.2 (Student) | uni_Student |

Each machine was joined by going to **This PC → Properties → Change Settings → Domain → uni.local**, providing administrator credentials, and rebooting. After joining, the computer objects were moved from the default `Computers` container into the appropriate department OU so that the correct GPOs apply to them.

## 4. Security Groups (RBAC)

Three **Global Security Groups** were created in the `uni_Groups` OU to implement **Role-Based Access Control (RBAC)** across the file server and all permission assignments:

| Group Name | Members |
|---|---|
| `Students-GRP` | All student user accounts |
| `Staff-GRP` | All staff/faculty user accounts |
| `Management-GRP` | All management/admin user accounts |

Permissions are assigned to **groups, not individual users**. This means adding or removing a user from a department only requires adding/removing them from the group — access is updated everywhere automatically.

## 6. Centralized File Server

### 6.1 Shared Folder Structure

A parent shared folder named **"Uni Shared Folder"** was created on the server (located at `C:\Users\Administrator\Desktop\Uni Shared Folder`). Three department-specific sub-folders were created inside it:

```
Uni Shared Folder\
├── Shared-Students\     (created 6/27/2026 1:58 PM)
├── Shared-Staff\        (created 6/27/2026 1:58 PM)
└── Shared-Management\   (created 6/27/2026 1:58 PM)
```

The parent folder was shared on the network as `\\30.0.0.20\Uni Shared Folder`, making all three sub-folders accessible to domain clients.

### 6.2 NTFS (Security) Permissions

NTFS permissions were configured on the folder via **Properties → Security tab** following the **Principle of Least Privilege**:

| Principal | Permissions Granted |
|---|---|
| Authenticated Users | Read & Execute, List Folder Contents, Read |
| SYSTEM | Full Control |
| Administrator | Full Control |
| Administrators (UNI\Administrators) | Full Control |

For each department sub-folder (Shared-Students, Shared-Staff, Shared-Management), the corresponding security group (Students-GRP, Staff-GRP, Management-GRP) was granted access while inheritance from the parent was broken to ensure **strict isolation between departments**.

### 6.3 Share (Network) Permissions

Configured via **Properties → Sharing → Advanced Sharing → Permissions**:

| Principal | Permissions |
|---|---|
| Authenticated Users | Full Control ✓, Change ✓, Read ✓ |

The combination of Share Permissions (allowing all authenticated users through the network share) and NTFS Permissions (restricting access to the correct department group at the file-system level) provides the real enforcement — NTFS is always the stricter layer.

### 6.4 Access Control Verification

A **Student account** logged onto a client machine and navigated to `\\30.0.0.20\Uni Shared Folder`:
- **Shared-Students** → Access granted ✓
- **Shared-Staff** → Received the error: *"Windows cannot access \\30.0.0.20\Uni Shared Folder\Shared-Staff. You do not have permission to access..."* ✗

This confirmed that NTFS permissions correctly enforced cross-department access isolation.

## 7. Group Policy Objects (GPO)

All GPOs were created and linked through **Server Manager → Tools → Group Policy Management**. The procedure for every policy was:
1. Right-click the target OU → **"Create a GPO in this domain, and Link it here…"**
2. Name the GPO, then right-click it → **Edit** to open the Group Policy Management Editor.
3. Navigate to the appropriate node (User Configuration or Computer Configuration) and enable the required setting.

### 7.1 Students GPO — uni_Student OU (Most Restrictive)

14 GPOs were created and linked to `uni_Student`, each targeting a specific restriction:

| # | GPO Name | Policy Path | Setting Enabled |
|---|---|---|---|
| 1 | Close Control Panel | User Config → Admin Templates → Control Panel | Prohibit access to Control Panel and PC settings |
| 2 | Prevent Registry editor | User Config → Admin Templates → System | Prevent access to registry editing tools |
| 3 | Prevent access to Task Manager | User Config → Admin Templates → System → Ctrl+Alt+Del Options | Remove Task Manager |
| 4 | No Wallpaper | User Config → Admin Templates → Desktop → Desktop | Desktop Wallpaper (path left blank) |
| 5 | USB lock | Computer Config → Admin Templates → System → Removable Storage Access | All Removable Storage classes: Deny all access |
| 6 | Hide Drivers | User Config → Admin Templates → Windows Components → File Explorer | Hide these specified drives in My Computer |
| 7 | Can't change Password | User Config → Admin Templates → System → Ctrl+Alt+Del Options | Remove Change Password |
| 8 | Prevent Access to shutdown | User Config → Admin Templates → System → Ctrl+Alt+Del Options | Remove Shut Down, Restart, Sleep, and Hibernate |
| 9 | Hide Network | User Config → Admin Templates → Network → Network Connections | Prohibit access to properties of a LAN connection / hide Network icon |
| 10 | Logon Banner | Computer Config → Policies → Windows Settings → Security Settings → Local Policies → Security Options | Interactive logon: Message title + Message text |
| 11 | Prevent Access of date and time | User Config → Admin Templates → Control Panel | Hide Date and Time icon / prevent modification |
| 12 | CMD | User Config → Admin Templates → System | Prevent access to the command prompt |
| 13 | Logon Hours | Enforced both via per-user AD account settings AND a linked GPO | Restricts login to authorized working hours |
| 14 | Close PowerShell | User Config → Admin Templates → System | Don't run specified Windows applications (powershell.exe) |

**GPO Enforcement Confirmed:** A student account on a domain-joined machine attempted to open a restricted application and received the pop-up: *"Restrictions — This operation has been cancelled due to restrictions in effect on this computer. Please contact your system administrator."*

## 8. Password Policy

Configured under **Default Domain Policy → Computer Configuration → Windows Settings → Security Settings → Account Policies → Password Policy**:

| Setting | Purpose |
|---|---|
| Enforce Password History | Prevents reusing recently used passwords |
| Minimum Password Length | Enforces a minimum character count |
| Password Must Meet Complexity Requirements | Requires uppercase, lowercase, digits, and symbols |
| Maximum Password Age | Forces periodic password changes |

---

## 9. Account Lockout Policy

Configured under **Default Domain Policy → Account Policies → Account Lockout Policy**:

| Setting | Purpose |
|---|---|
| Account Lockout Threshold | Number of failed logon attempts before the account locks |
| Account Lockout Duration | How long the account stays locked before auto-reset |
| Reset Account Lockout Counter After | The time window for counting failed attempts |

This policy directly mitigates **brute-force and password spraying attacks** by automatically locking accounts that receive too many wrong password attempts.

## 10. Security Logon Banner

Configured via **Computer Configuration → Policies → Windows Settings → Security Settings → Local Policies → Security Options**:

- **Interactive logon: Message title for users attempting to log on** → set to a warning title (e.g., "Authorized Users Only").
- **Interactive logon: Message text for users attempting to log on** → set to a full warning message notifying users that the system is monitored and restricted to authorized personnel.

This banner appears **before** the credential prompt on every domain-joined workstation, serving both as a legal notice and a security deterrent.

## 11. Logon Hours

Logon hours were configured **per individual user account** via:
**Active Directory Users and Computers → User Properties → Account tab → Logon Hours button**

In the grid view (days of the week vs. hours of the day):
- **Blue (Logon Permitted)** blocks were selected for working hours (Sunday through Thursday, specific hour ranges).
- **White (Logon Denied)** blocks were left for off-hours (evenings, Friday, Saturday).

This prevents users from logging onto the domain outside authorized working hours. The **"Logon Houres" GPO** was also linked to each OU to enforce this at the policy level in addition to the per-user setting.

## 12. Windows Security Auditing

Advanced Audit Policies were enabled through **Group Policy Management Editor → Computer Configuration → Policies → Windows Settings → Security Settings → Advanced Audit Policy Configuration**:

| Audit Category | What is Logged |
|---|---|
| Logon / Logoff | Every successful and failed logon/logoff event |
| Account Management | User account creation, deletion, modification; group changes |
| Object Access | File system access; file share access |
| Policy Change | Changes to the audit policy itself or security settings |
| Computer Account Management | Computer objects joining/leaving the domain |

For file-system auditing to generate events, a **SACL (System Access Control List)** was also added to the shared folders via **Properties → Security → Advanced → Auditing**, specifying which access types (Read, Write, Delete) trigger audit log entries and for which users/groups.

## 17. Security Architecture Summary

The overall security posture implemented on this server follows four layers:

**Layer 1 — Identity & Access (AD DS)**
Centralized authentication via Kerberos; all users must authenticate against the domain before accessing any resource. No local accounts are used for network resources.

**Layer 2 — Endpoint Hardening (GPO)**
14 policies on Students, 8 on Staff, 7 on Management — each progressively relaxed as privilege increases. Students have the most restricted desktop environment (no CMD, no PowerShell, no Control Panel, no USB, no registry). Staff and Management retain more usability but are still locked down on critical vectors (registry, task manager, PowerShell, USB for Management).

**Layer 3 — Resource Access Control (NTFS + Share Permissions)**
Every department folder is siloed — a user in Students-GRP cannot read, write, or even list the contents of Shared-Staff or Shared-Management. Access Denied is enforced at the NTFS layer, which cannot be bypassed even with share-level access.

**Layer 4 — Monitoring & Auditing (Audit Policy + Event Viewer)**
Every logon, logoff, account change, file access, and policy change is written to the Security event log. With 147,041+ events recorded, the audit trail provides full accountability and supports incident investigation.
